# 38 · 输入处理与渲染 (Inputs & Renderers)

> 对应目录：`vllm/inputs/`、`vllm/renderers/`、`vllm/v1/engine/input_processor.py`

## 这个模块负责什么

把"用户给的各种形式的输入"统一转换成"模型能直接吃的格式"。这是请求进入引擎前的**预处理流水线**。

类比 Web 后端：这是请求进入业务逻辑前的一系列 Filter / 参数绑定 / 校验。

## 输入形式有多乱

用户的输入可能是：

- 一个字符串：`"你好"`
- 已经分好词的 token：`{"prompt_token_ids": [108386]}`
- 一段对话：`[{"role": "user", "content": "你好"}]`
- 带图片：`{"prompt": "...", "multi_modal_data": {"image": ...}}`

模型只认一种东西：token id 序列（外加可能的多模态特征）。渲染和输入处理就是把上面五花八门的输入收敛成这一种。

## 两个阶段：渲染 (Render) → 处理 (Process)

### 1. 渲染 (Renderers)

`vllm/renderers/` 负责"把高层输入变成 prompt"。最典型的就是**聊天渲染**：把 `messages` 对话列表套上模型的聊天模板，变成一段文本。

```
[{"role":"user","content":"你好"}]
  ↓ renderer 应用聊天模板
"<|user|>\n你好<|assistant|>\n"
```

不同模型模板不同，所以 `renderers/` 下按模型/家族分了文件（`mistral.py`、`deepseek_v4.py`、`hf.py` 等），由 `registry.py` 注册管理。`hf.py` 是通用的 HuggingFace 模板渲染。

> 注意区分：`renderers/` 是较新的统一渲染层；`entrypoints/chat_utils.py`（见 `23`）也做聊天模板处理。vLLM 正在往统一的 Renderer 流水线收敛（代码注释里能看到 "planned Renderer refactor"）。

### 2. 输入处理 (Input Processor)

`v1/engine/input_processor.py` 的 `process_inputs()`（回顾 `02-引擎.md` 的 `add_request` 调的就是它）负责：

```
prompt 文本 / 对话
  ↓ tokenize（见 18-分词器）
token id 序列
  +
多模态数据
  ↓ 多模态预处理（见 11-多模态）
图像/音频特征 + 占位符
  ↓
构造成引擎内部的 Request（见 27-核心数据结构）
```

## 完整预处理流水线

把它放进请求生命周期（呼应 `07`）：

```
用户输入（字符串/对话/多模态）
  ↓ ① Render：对话 → prompt 文本（套聊天模板）
  ↓ ② Tokenize：文本 → token id
  ↓ ③ 多模态处理：图片/音频 → 特征 + 占位符
  ↓ ④ 组装：→ Request 对象
进入引擎调度（03 起）
```

## 代码结构

| 目录/文件 | 作用 |
|-----------|------|
| `renderers/` | 渲染层：高层输入 → prompt（聊天模板等） |
| `renderers/registry.py` | 渲染器注册表（按模型选） |
| `inputs/` | 输入数据类型定义（PromptType 等，见 27） |
| `v1/engine/input_processor.py` | 输入处理主逻辑：tokenize + 多模态 + 组装 |

## 为什么这层值得了解

- 它是"用户输入"和"模型输入"之间的翻译层，很多"格式不对/模板错误"的问题出在这
- 聊天模板用错会导致模型表现异常（比如角色标记不对），排查时要看这层
- 加新模型时，可能需要为它写/适配渲染逻辑（结合 `14`、`13`）

## 小结

- 输入处理 = 把五花八门的用户输入统一成模型能吃的 token 序列
- 两阶段：渲染（对话→prompt，套聊天模板）+ 处理（tokenize + 多模态 + 组装 Request）
- `renderers/` 按模型注册模板，`input_processor.py` 做主处理
- 是请求进引擎前的预处理流水线，格式类问题常出在这
