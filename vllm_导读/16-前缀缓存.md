# 16 · 前缀缓存 (Prefix Caching)

> 对应文件：`vllm/v1/core/block_pool.py`、`vllm/v1/core/kv_cache_utils.py`、`vllm/v1/core/kv_cache_manager.py`

## 一句话

如果两个请求的开头（前缀）相同，那这段前缀的计算结果可以**复用**，不用重复算。这就是前缀缓存。

## 为什么有用

很多请求有相同的开头：

- 系统提示词："你是一个有帮助的助手……"（所有请求都带）
- 多轮对话：第二轮请求 = 第一轮的全部内容 + 新问题
- few-shot 示例：同样的示例前缀 + 不同的问题

这些相同前缀如果每次都重新算 KV Cache，是巨大的浪费。前缀缓存让它们只算一次。

类比：缓存（cache）思想，和 Web 后端的 Redis 缓存、CDN 缓存是一个道理——重复的东西算一次存起来，后面直接取。

## 工作原理：给块算 hash

回顾 `04-KVCache管理.md`：KV Cache 被切成固定大小的块（block）。前缀缓存的核心是给每个**填满的块**算一个 hash：

```
块的 hash = hash(这个块里的 token 内容 + 前面所有块的 hash)
```

注意 hash 包含了"前面所有块"，所以只有**前缀完全相同**的块 hash 才相同。这保证了复用的正确性。

## 命中流程

新请求进来时（回顾 `03-调度器.md` 的阶段 B）：

```
请求的 prompt
  ↓ 切成块，逐块算 hash
  ↓ 拿 hash 去 block_pool 查：这个块之前算过吗？
  ├─ 命中：直接复用那个物理块（不用重算！）
  └─ 未命中：分配新块，正常计算
```

对应代码 `kv_cache_manager.py` 的 `get_computed_blocks()`：

```python
def get_computed_blocks(self, request):
    computed_blocks, num_computed = self.coordinator.find_longest_cache_hit(
        request.block_hashes, max_cache_hit_length
    )
    return computed_blocks, num_computed
```

它返回"已经算过的块"和"已命中的 token 数"。命中的部分，请求的 `num_computed_tokens` 直接跳过这些，从未命中处开始算。

## 块共享与引用计数

多个请求可以**同时指向同一个物理块**（因为内容相同）。block_pool 用**引用计数**管理：

```
块 #5（系统提示词的一部分）
  ├─ 请求 A 在用  ┐
  ├─ 请求 B 在用  ├─ 引用计数 = 3
  └─ 请求 C 在用  ┘
```

只有当引用计数归零（没人用了），这个块才能被回收/驱逐。

## 驱逐策略 (Eviction)

缓存空间有限，块用完后不会立刻清空，而是先留着（万一有请求能复用）。当需要新块但池子满了时，按 **LRU（最近最少使用）** 驱逐那些没人引用、最久没被用到的块。

这又是经典缓存思想：和操作系统的页面置换、Redis 的淘汰策略一脉相承。

## 收益有多大

在有大量共享前缀的场景（多轮对话、统一系统提示词、RAG），前缀缓存能把 prefill 阶段的计算量砍掉一大半，首 token 延迟（TTFT）显著下降。

## 怎么控制

前缀缓存默认开启。可以关闭：

```python
llm = LLM(model="...", enable_prefix_caching=False)
```

## 小结

- 前缀缓存 = 相同开头的请求复用已算好的 KV Cache
- 原理：给每个块算包含前缀信息的 hash，hash 相同就复用
- 多请求靠引用计数共享物理块，满了按 LRU 驱逐
- 在多轮对话、统一系统提示词等场景收益巨大
- 和后端的缓存思想完全相通（Redis/CDN/页面置换）
