# 20 · 平台抽象与硬件后端 (Platforms)

> 对应目录：`vllm/platforms/`

## 这个模块负责什么

vLLM 不只跑在 NVIDIA GPU 上，还支持 AMD GPU、Intel GPU、Google TPU、CPU 等。平台抽象层把"硬件相关的差异"封装起来，让上层代码不用关心底层是什么硬件。

类比 Web 后端：像 JDBC 之于不同数据库，或 JVM 之于不同操作系统——上层写一套代码，底层适配不同实现。

## 支持的平台

| 文件 | 平台 |
|------|------|
| `platforms/cuda.py` | NVIDIA GPU（主流，最完善） |
| `platforms/rocm.py` | AMD GPU |
| `platforms/xpu.py` | Intel GPU |
| `platforms/tpu.py` | Google TPU |
| `platforms/cpu.py` | CPU（无 GPU 时） |
| `platforms/interface.py` | 抽象接口（所有平台要实现的契约） |

## 核心设计：统一接口 + 各自实现

`platforms/interface.py` 定义了一个抽象基类 `Platform`，规定了所有平台必须回答的问题，比如：

```python
class Platform:
    def is_available(self): ...           # 这个平台现在能用吗
    def get_device_name(self): ...        # 设备叫什么名字
    def get_attn_backend(self): ...       # 用哪个 attention 实现
    def inference_mode(self): ...         # 推理模式设置
    def check_and_update_config(self): ...# 根据硬件特性调整配置
    ...
```

每个具体平台（cuda、rocm…）继承并实现这些方法。启动时 vLLM 自动检测当前硬件，选用对应的 Platform 实现。这是典型的**策略模式 / 适配器模式**。

## 为什么需要这层抽象

不同硬件差异很大：

- attention kernel 不同（NVIDIA 用 FlashAttention，AMD 用自己的实现）
- 通信库不同（NVIDIA 用 NCCL，其他平台有各自的）
- 支持的数据类型不同（不是所有硬件都支持 FP8）
- 显存管理方式不同

如果不抽象，上层代码会塞满 `if cuda: ... elif rocm: ...` 的判断。有了平台层，上层只管调用统一接口，差异都收敛在 `platforms/` 里。

## 自动检测

`platforms/__init__.py` 在启动时探测环境（有没有 CUDA、是不是 AMD 卡……），返回当前平台对象。之后全局通过这个对象访问硬件能力。

## 和其他模块的关系

平台层很底层，几乎被所有需要碰硬件的模块依赖：

- worker 初始化时问平台"用哪个 attention 后端"
- 分布式模块问平台"用哪个通信库"
- 配置校验时问平台"支持这个 dtype 吗"

## 对新手的意义

- 如果你只用 NVIDIA GPU，大多数时候不用关心这层
- 但理解它的存在，能解释为什么 vLLM 能跨硬件、代码里为什么有那么多"后端选择"逻辑
- 给特定硬件做适配/优化是进阶贡献方向（`[Hardware][Vendor]` 类型的 PR）

## 小结

- 平台层封装硬件差异，让上层代码硬件无关
- 支持 NVIDIA / AMD / Intel GPU、TPU、CPU
- 设计：统一抽象接口（`interface.py`）+ 各平台实现，启动自动检测
- 典型的适配器/策略模式，是 vLLM 跨硬件能力的基础
