# 28 · 注意力后端 (Attention Backends)

> 对应目录：`vllm/v1/attention/`、`vllm/model_executor/layers/attention/`

## 先理解：注意力是什么、为什么重要

注意力（Attention）是 Transformer 的核心运算：生成每个 token 时，模型要"回看"前面所有 token，算出哪些更相关，加权汇总。

它是**最耗时、最耗显存**的部分（KV Cache 就是为它服务的）。所以注意力的实现质量直接决定 vLLM 的性能。

类比：如果说模型 forward 是一场比赛，注意力就是最关键的赛段，vLLM 在这里投入了最多的优化。

## 为什么需要"多个后端"

注意力的计算方式有很多种实现，各有适用场景和硬件要求。vLLM 不绑死一种，而是抽象出"注意力后端（backend）"，运行时根据硬件和场景**自动选最合适的**。

类比：JDBC 之于不同数据库驱动——统一接口，多种实现，按环境选用。

## 常见的注意力后端

| 后端 | 特点 | 适用 |
|------|------|------|
| FlashAttention | 业界标杆，省显存、快 | NVIDIA GPU 主流选择 |
| FlashInfer | 针对推理优化，对分页 KV 友好 | NVIDIA，部分场景更快 |
| Triton 实现 | 用 Triton 写的，跨硬件较好 | 没有 FlashAttention 时的备选 |
| ROCm/XPU 等 | 各家硬件自己的实现 | AMD/Intel 等平台 |

> FlashAttention 的核心思想：不把巨大的注意力矩阵整个存到显存，而是分块计算、边算边汇总，大幅省显存。这是现代 LLM 推理的基础优化。

## 代码结构

```
v1/attention/
├── backend.py     ← 后端抽象接口（所有后端要实现的契约）
├── selector.py    ← 选择器：根据硬件/配置挑后端
└── backends/      ← 各个具体后端的实现
```

`selector.py` 是入口：启动时它检查"什么硬件、什么模型、装了哪些库"，然后选定一个后端。回顾 `20-平台抽象与硬件后端.md`，平台对象的 `get_attn_backend()` 就参与这个选择。

## 注意力后端做的两件事

1. **build metadata（构建元数据）**：把调度器给的信息（每个请求的 KV 块位置 = block table）整理成 kernel 需要的格式。回顾 `05-Worker模型执行.md` 的 `_build_attention_metadata`，它针对选定的后端构建对应的 metadata。
2. **forward（执行计算）**：调用底层 kernel（多在 `csrc/`，见 `21`），完成"读 KV → 算注意力分数 → 加权求和"。

## 和 PagedAttention 的关系

PagedAttention（见 `04`）是 vLLM 的分页 KV 管理思想；注意力后端是"在这种分页结构上高效算注意力"的具体实现。两者配合：

```
KVCacheManager 分配分页的 KV 块（04）
        ↓ block table（哪个请求用哪些块）
注意力后端 kernel 按 block table 从分散的块里读 KV，算注意力（28）
```

后端必须支持"从不连续的物理块读 KV"，这正是它和普通注意力实现的关键区别。

## 高级特性：Cascade Attention

代码里出现的 `cascade_attn`：当一批请求**共享很长的公共前缀**（见 `16-前缀缓存.md`）时，可以把"公共前缀的注意力"只算一次，再和各请求私有部分合并，进一步省算力。这是注意力层和前缀缓存协同的优化。

## 对新手的意义

- 知道"注意力是最关键的运算，vLLM 用可插拔后端 + FlashAttention 类 kernel 优化它"就够了
- 平时不用手动选后端，vLLM 自动处理
- 想深入性能/做硬件适配时，这是核心战场（结合 `21-自定义算子与CUDA内核.md`）

## 小结

- 注意力是 Transformer 最耗时的核心运算，KV Cache 为它服务
- vLLM 抽象出可插拔的注意力后端，按硬件/场景自动选（FlashAttention 等）
- 后端负责：构建 metadata（block table）+ 调 kernel 算注意力
- 它是 PagedAttention 思想在计算层的落地，必须支持从分页块读 KV
