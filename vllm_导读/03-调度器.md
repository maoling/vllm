# 03 · 调度器 (Scheduler)

> 对应文件：`vllm/v1/core/sched/scheduler.py`

## 这个模块负责什么

调度器决定**每一步 GPU 该处理哪些请求、各处理多少 token**。它是 vLLM 高吞吐的关键。

类比 Web 后端：这是**线程池调度器 + 请求队列管理**，但比 Tomcat 的复杂得多——因为所有请求共享一块 GPU，要在有限的显存里挤进尽可能多的请求。

## 先理解一个关键概念：没有 prefill/decode 之分

传统理解里，LLM 推理分两阶段：

- **Prefill（预填充）**：一次性处理整个 prompt（比如 100 个 token）
- **Decode（解码）**：之后每步只生成 1 个 token

vLLM 调度器的巧妙之处：**它不区分这两个阶段**。源码注释（`scheduler.py` 第 390 行）说得很清楚：

> 每个请求只有两个数字：`num_computed_tokens`（已经算完的 token 数）和 `num_tokens_with_spec`（总共需要算的 token 数）。调度器每一步都尝试让前者追上后者。

这个统一抽象同时覆盖了 chunked prefill（把长 prompt 切块）、prefix caching（前缀复用）、speculative decoding（推测解码）等高级特性。

## 三个队列

调度器管理着请求的不同状态：

| 队列 | 含义 | 类比 |
|------|------|------|
| `waiting` | 等待中的新请求 | 任务等待队列 |
| `running` | 正在生成的请求 | 运行中的线程 |
| （被抢占） | 显存不够被踢出去的请求 | 被换出的任务 |

## schedule() 的两个阶段

`schedule()` 方法（第 388 行）核心逻辑分两步走。

### 阶段 A：优先调度 RUNNING（运行中）的请求

```python
token_budget = self.max_num_scheduled_tokens   # 本轮 token 预算

while req_index < len(self.running) and token_budget > 0:
    request = self.running[req_index]

    # 这个请求还需要算多少 token
    num_new_tokens = request.num_tokens_with_spec - request.num_computed_tokens
    num_new_tokens = min(num_new_tokens, token_budget)   # 不能超预算

    # 尝试分配 KV Cache 显存块
    new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens)

    if new_blocks is None:
        # 显存不够！抢占（踢掉）队尾的请求
        preempted_req = self.running.pop()
        self._preempt_request(preempted_req, ...)
    else:
        # 成功安排
        num_scheduled_tokens[request.request_id] = num_new_tokens
        token_budget -= num_new_tokens
```

> **抢占（Preemption）** 是关键机制：当显存不够时，调度器会把某些请求"踢出"运行队列，释放它们的显存块给更紧急的请求。被踢的请求之后会重新排队。这类似操作系统的内存换页，或 JVM 的 OOM 处理。

### 阶段 B：接纳 WAITING（等待中）的新请求

```python
while self.waiting and token_budget > 0:
    if len(self.running) == self.max_num_running_reqs:
        break   # 运行队列满了

    request = request_queue.peek_request()

    # 查找前缀缓存：如果这个 prompt 的前缀之前算过，直接复用
    computed_blocks, num_computed = self.kv_cache_manager.get_computed_blocks(request)

    # 分配显存块
    new_blocks = self.kv_cache_manager.allocate_slots(request, ...)
    if new_blocks is None:
        break   # 没显存了，停止接纳新请求

    # 成功！移入 running 队列
    self.running.append(request)
```

## Continuous Batching（连续批处理）

这是 vLLM 的另一大杀器。传统批处理要等一批请求全部完成才能开始下一批；vLLM 允许：

- 新请求随时加入正在运行的 batch
- 完成的请求随时离开，腾出的空间立刻给新请求

效果：GPU 几乎不会空转，吞吐量大幅提升。这个能力正是来自 `schedule()` 每一步都重新评估所有队列。

## 调度策略

vLLM 支持两种策略（`SchedulingPolicy`）：

- **FCFS**（先来先服务，默认）：按到达顺序
- **PRIORITY**（优先级）：按请求的优先级，抢占时踢掉优先级最低的

## schedule() 输出什么

最终返回一个 `SchedulerOutput` 对象，里面包含：

- 本轮要处理哪些请求
- 每个请求处理多少 token
- 每个请求的 KV Cache 块在哪里（block table）

这个对象会被交给 GPU worker 执行（见 `05-Worker模型执行.md`）。

## 小结

- 调度器决定"每一步 GPU 处理哪些请求、各多少 token"
- 核心抽象：不分 prefill/decode，只看"已算 vs 待算"的 token 数
- 两阶段：先推进运行中的，再接纳等待中的
- 关键机制：抢占（显存不够踢人）+ 连续批处理（动态进出 batch）
