# 12 · 推测解码 (Speculative Decoding)

> 对应目录：`vllm/v1/spec_decode/`

## 要解决的问题

大模型逐字生成很慢：每生成 1 个 token 就要把整个大模型跑一遍 forward。而 GPU 其实"算力有富余、卡在访存"——跑一遍模型，多算几个 token 的边际成本并不高。

推测解码就是利用这一点来加速。

## 核心思想：先猜后验

类比考试：与其一题一题慢慢想（大模型逐字生成），不如：

1. 找个"学渣助手"（小模型）快速猜出接下来好几个 token
2. 让"学霸"（大模型）一次性批量检查这几个猜测
3. 猜对的部分直接采纳，猜错的地方从那里重新来

因为大模型"批量检查 5 个 token"和"生成 1 个 token"耗时差不多，只要猜得够准，就能用一次大模型的开销产出多个 token，**速度数倍提升，且输出质量不变**（数学上保证和大模型自己生成的分布一致）。

## 几种"猜测"的方式

vLLM 支持多种 proposer（猜测器），文件都在 `v1/spec_decode/`：

| 方式 | 文件 | 怎么猜 |
|------|------|--------|
| 草稿模型 | `draft_model.py` | 用一个独立的小模型来猜 |
| EAGLE | `eagle.py` | 用大模型的隐藏状态训练一个轻量预测头来猜，更准 |
| Medusa | `medusa.py` | 给大模型加多个预测头，一次猜多个位置 |
| N-gram | `ngram_proposer.py` | 不用模型，直接从上下文里找重复片段来猜（适合有大量重复的场景，如改写、RAG） |
| Suffix | `suffix_decoding.py` | 基于后缀匹配的猜测 |

## 流程图

```
当前文本: "今天天气"
   │
   ▼
① 猜测器快速猜出 N 个 token: ["很", "好", "，", "适合", "出门"]
   │
   ▼
② 大模型一次性验证这 5 个猜测（一次 forward）
   │
   ▼
③ 逐个对比：
   "很"   ✓ 接受
   "好"   ✓ 接受
   "，"   ✓ 接受
   "适合" ✗ 拒绝 → 用大模型自己的结果替换，后面的丢弃
   │
   ▼
本轮净产出: "很好，" + 大模型纠正的 1 个 token = 4 个 token（只花了 1 次大模型开销）
```

## 关键概念：接受率

推测解码的收益取决于**猜测的接受率**：

- 猜得准（接受率高）→ 加速明显
- 猜得差（接受率低）→ 白白浪费验证开销，可能反而变慢

所以猜测器的质量很重要，EAGLE 这类方法就是为了提高接受率而设计的。

## 它如何融入主循环

回顾 `02-引擎.md` 的四步循环，推测解码主要影响调度和验证：

- 调度时，请求带着"草稿 token"（`spec_token_ids`）一起被安排
- 大模型一次 forward 同时计算这些草稿位置
- 采样阶段做"接受/拒绝"判断（`v1/sample/` 里的 rejection sampling）
- 接受的草稿 token 直接计入已生成，跳过了多次大模型调用

调度器代码里能看到 `num_scheduled_spec_tokens`、`scheduled_spec_decode_tokens` 这些就是处理草稿 token 的。

## 怎么用

```python
llm = LLM(
    model="meta-llama/Llama-3-70B",
    speculative_config={
        "model": "meta-llama/Llama-3-8B",  # 用 8B 当草稿模型猜
        "num_speculative_tokens": 5,        # 每次猜 5 个
    },
)
```

## 小结

- 推测解码 = 小模型/轻量方法快速猜，大模型批量验证，加速生成
- 利用了"大模型批量验证 ≈ 生成一个 token"的特性
- 关键是接受率：猜得准才省时间
- 多种猜测方式：草稿模型、EAGLE、Medusa、N-gram 等
- 输出质量不变（数学上等价于大模型自己生成）
