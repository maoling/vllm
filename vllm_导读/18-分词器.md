# 18 · 分词器 (Tokenizer)

> 对应目录：`vllm/tokenizers/`、`vllm/transformers_utils/`

## 什么是分词器

模型不认识文字，只认数字（token id）。分词器（tokenizer）就是文字和数字之间的翻译官：

- **编码 (encode)**：文字 → token id 列表（请求进来时）
- **解码 (decode)**：token id → 文字（结果出去时）

```
"你好世界"
  ↓ encode
[108386, 124700]
  ↓ 模型处理、生成新 token
[108386, 124700, 6447, ...]
  ↓ decode
"你好世界！..."
```

## token 是什么

token 不一定是一个完整的字或词，而是"子词单元"。比如英文 "unhappy" 可能被切成 `["un", "happy"]`，中文一个字通常是一个或多个 token。词表（vocabulary）就是所有 token 的清单，大模型词表通常有几万到十几万个 token。

## 在请求生命周期里的位置

回顾 `07-请求生命周期.md`：

- **入口处**（`LLMEngine.add_request`）：把用户的 prompt 文本 encode 成 token id
- **输出处**（`OutputProcessor` / detokenizer）：把模型生成的 token id decode 回文字

## 增量解码 (Incremental Detokenization)

一个值得注意的细节：流式输出时，模型一个一个吐 token，分词器要**增量地**把它们拼成文字。

这里有个坑：有些字符要几个 token 才能拼出来（比如一个 emoji 或某些中文）。如果某个 token 单独 decode 是乱码，分词器要"攒着"等后续 token 一起 decode。这个逻辑在 `v1/engine/detokenizer.py` 里处理。

```
token: [片段1] → decode → "�"（还不完整，先攒着）
token: [片段2] → decode → "好"（凑齐了，输出）
```

## 代码结构

| 目录/文件 | 作用 |
|-----------|------|
| `tokenizers/` | 分词器封装 |
| `transformers_utils/` | 对接 HuggingFace tokenizer、模型配置等 |
| `v1/engine/detokenizer.py` | 增量解码逻辑 |

## 性能：为什么有 Rust 前端

分词在高并发时也是 CPU 开销。大多数分词器底层用 Rust 实现（HuggingFace 的 `tokenizers` 库就是 Rust 写的），速度很快。vLLM 还有实验性的 Rust 前端（项目根目录 `rust/`），进一步减少高并发场景下的 tokenize/请求处理开销。

这也回应了之前的问题——为什么 vLLM 用 Python 还能快：真正的热点（分词、矩阵运算）都在 Rust/C++/CUDA 里，Python 只做编排。

## 特殊 token

词表里有一些特殊 token，不是普通文字，而是控制信号：

| 特殊 token | 含义 |
|-----------|------|
| EOS (end of sequence) | 生成结束标志，模型吐出它就停止 |
| BOS (begin of sequence) | 序列开始 |
| PAD | 填充（对齐 batch 用） |
| 聊天模板 token | 标记对话角色，如 `<|user|>`、`<|assistant|>` |

采样时遇到 EOS 就知道该停了（回顾 `06-采样.md` 的停止条件）。`skip_special_tokens` 参数控制 decode 时是否把这些特殊 token 显示出来。

## 小结

- 分词器 = 文字↔token id 的翻译官，encode 进、decode 出
- token 是"子词单元"，词表是所有 token 的清单
- 流式输出需要增量解码，要处理"半个字符"的情况
- 底层用 Rust 实现，速度快，是 vLLM 性能不受 Python 拖累的又一例证
- 特殊 token（EOS 等）是控制信号，影响生成停止
