# 37 · 性能剖析 (Profiling)

> 对应目录：`vllm/profiler/`、`docs/contributing/profiling.md`

## 这个模块负责什么

帮你回答："时间/显存到底花在哪了？" 当你想优化性能或找瓶颈时，profiling（性能剖析）让你看到每个操作的耗时和资源占用。

类比 Web 后端：像 Java 的 JProfiler、async-profiler，或 Python 的 cProfile——但这里要剖析的是 GPU 上的运算。

## Profiling vs Metrics vs Tracing

容易和 `22`、`31` 混淆，区分一下：

| 工具 | 粒度 | 回答 | 用在 |
|------|------|------|------|
| Metrics（22） | 系统级 | 整体吞吐/延迟如何 | 生产监控 |
| Tracing（31） | 请求级 | 单个请求各阶段耗时 | 定位慢请求 |
| Profiling（37） | 算子级 | 每个 kernel/操作耗多少 | 深度优化、开发 |

Profiling 最细，深入到"哪个矩阵乘法、哪个 kernel 花了多少微秒"。

## 两种剖析方式

### 1. PyTorch Profiler

vLLM 集成了 PyTorch 自带的 profiler。可以录制一段运行，生成详细的算子耗时报告，能在 Chrome trace / TensorBoard 里可视化。

通过接口触发（回顾 `entrypoints/llm.py` 里的方法）：

```python
llm.start_profile()
llm.generate(...)      # 这段会被剖析
llm.stop_profile()
# 生成 trace 文件，可视化分析
```

或用环境变量 `VLLM_TORCH_PROFILER_DIR` 指定输出目录（见 `36-环境变量与运行时开关.md`）。

### 2. Layerwise Profiler（逐层剖析）

`profiler/layerwise_profile.py` 提供更贴合 vLLM 的逐层剖析：看模型每一层（注意力、FFN、norm 等）各花多少时间和显存。这对定位"哪一层是瓶颈"很有用。

## 代码结构

| 文件 | 作用 |
|------|------|
| `profiler/layerwise_profile.py` | 逐层耗时/显存剖析 |
| `profiler/wrapper.py` | 剖析器封装 |
| `profiler/utils.py` | 工具函数 |

## 典型的剖析能发现什么

```
剖析报告（示意）：
  attention kernel       45%  ← 最大头，注意力是瓶颈（符合预期）
  FFN / MoE              30%
  layernorm + 其他        10%
  采样                    3%
  Python 调度开销         2%   ← 印证：Python 开销很小（见 总览的性能讨论）
  通信（多卡）            10%
```

这种数据能指导优化方向：是该换更快的注意力后端（`28`）？还是该开 CUDA Graph 减少开销（`17`）？还是通信成了瓶颈（`08`）？

## 和"试运行"profiling 区别

注意：`02-引擎.md` 提到引擎初始化时有个 `_initialize_kv_caches` 的"试运行"，那是**显存探测**（估算能分多少 KV 块），目的不同——那是为了规划显存，不是性能剖析。本篇说的 profiling 是开发/优化时主动触发的性能分析。

## 对新手的意义

- 学习阶段一般用不到，了解"有这么个工具"即可
- 当你想做性能优化、或好奇时间花在哪时，profiling 是最直接的手段
- 它能用数据验证很多结论（比如"Python 真的不是瓶颈"）
- 给 vLLM 做性能优化贡献时，profiling 是必备工具（配合 `22` 的 benchmark）

## 小结

- Profiling = 算子级的性能剖析，看每个操作的耗时/显存
- 比 Metrics（系统级）、Tracing（请求级）更细
- 两种方式：PyTorch Profiler（通用）+ Layerwise Profiler（逐层）
- 用于定位瓶颈、指导优化、验证性能假设
- 和初始化时的"显存探测试运行"不是一回事
