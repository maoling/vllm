# 32 · 睡眠唤醒与权重更新 (Sleep/Wake & Weight Update)

> 对应：`LLM.sleep()` / `wake_up()`、`vllm/distributed/weight_transfer/`、`vllm/device_allocator/`

## 背景：RLHF 这类训练场景

这组功能主要服务一个特殊但重要的场景：**强化学习训练（RLHF）**，比如训练对话模型时常用的 PPO、GRPO 等算法。

这类训练有个特点：**训练和推理交替进行**。

```
循环：
  ① 用当前模型推理，生成一批回答（用 vLLM 推理）
  ② 根据回答的好坏打分，更新模型权重（训练框架做）
  ③ 把更新后的权重同步回 vLLM
  ④ 回到 ①，用新权重再生成
```

这就带来两个需求：**腾显存**和**热更新权重**。

## 一、睡眠与唤醒 (Sleep / Wake)

### 问题

训练（②）和推理（①）抢同一批 GPU 的显存。推理时 vLLM 占着大量显存（模型权重 + KV Cache）；轮到训练时，这些显存得让出来给训练用。

### 解法

`LLM.sleep()`：让 vLLM "睡觉"，释放显存：

```python
llm.sleep(level=1)   # 释放 KV Cache 等，权重可选择保留或卸载到 CPU
# ... 这段时间训练框架用 GPU 训练 ...
llm.wake_up()        # 唤醒，重新占用显存，准备推理
```

- **level 1**：释放 KV Cache，权重留在 GPU（唤醒快）
- **level 2**：连权重也卸载（省更多显存，唤醒慢一点）

底层靠 `device_allocator/`（自定义的显存分配器，`csrc/cumem_allocator.cpp`）实现"优雅地交出和收回显存"，而不用销毁整个引擎重建。

## 二、权重更新 (Weight Update)

### 问题

训练更新了权重后，要把新权重灌进 vLLM，但**不能重启服务**（重启太慢，且打断流程）。

### 解法

`vllm/distributed/weight_transfer/` 提供权重热更新机制。回顾 `entrypoints/llm.py` 里的方法：

```python
llm.start_weight_update()      # 开始更新
llm.update_weights(request)    # 把新权重传进来（可分片、分批）
llm.finish_weight_update()     # 完成
```

权重可以从训练进程**直接通过 GPU 通信传输**（不落盘），非常快。这对 RLHF 的迭代效率至关重要——每轮都要同步一次权重。

## 三者如何配合（RLHF 一轮）

```
vLLM 推理生成回答（占满显存）
  ↓ llm.sleep()         释放显存
训练框架用 GPU 更新权重（产生新权重）
  ↓ llm.wake_up()       vLLM 重新占显存
  ↓ llm.update_weights() 把新权重热更新进 vLLM
vLLM 用新权重继续推理
  ↓ 循环
```

## 对新手的意义

- 纯推理/部署场景**完全用不到**这些
- 但如果你做 RLHF、模型训练相关工作，这是 vLLM 一个很有价值的能力（很多 RLHF 框架如 OpenRLHF、veRL 都集成了 vLLM 的这套机制）
- 它体现了 vLLM 不只是"推理服务器"，也是"训练流程里的推理引擎"

## 小结

- 主要服务 RLHF 等"训练+推理交替"的场景
- Sleep/Wake：临时释放/收回 GPU 显存，把卡让给训练，不用重建引擎
- Weight Update：不重启服务，热更新模型权重，可经 GPU 直传
- 三者配合支撑 RLHF 的高效迭代循环
- 普通推理部署无需关心
