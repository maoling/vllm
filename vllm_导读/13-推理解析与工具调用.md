# 13 · 推理解析与工具调用 (Reasoning & Tool Parsing)

> 对应目录：`vllm/reasoning/`、`vllm/tool_parsers/`

## 背景

现代模型有两个常见能力，都需要从模型的原始输出里"解析出结构"：

1. **推理模型（Reasoning）**：像 DeepSeek-R1，会先输出一段"思考过程"，再给最终答案
2. **工具调用（Tool Calling / Function Calling）**：模型决定调用某个函数，输出函数名和参数

模型本身只会吐文本，这些"结构"是用特殊标记包裹的。解析器（parser）的工作就是把它们拆出来。

## 一、推理解析 (Reasoning Parser)

### 模型输出长什么样

推理模型的典型输出：

```
<think>
用户问 1+1，这是基础算术，答案是 2。
</think>
1 + 1 = 2
```

`<think>...</think>` 里是思考过程，外面是给用户的最终答案。

### 解析器要做什么

把这段输出拆成两部分：

- `reasoning_content`（思考过程）：`"用户问 1+1..."`
- `content`（最终答案）：`"1 + 1 = 2"`

这样 API 就能分开返回，前端可以选择显示或隐藏思考过程。

### 代码结构

`vllm/reasoning/` 下每个模型一个解析器：

| 文件 | 对应模型 |
|------|----------|
| `deepseek_r1_reasoning_parser.py` | DeepSeek-R1（用 `<think>` 标签） |
| `deepseek_v3_reasoning_parser.py` | DeepSeek-V3（可切换思考模式） |
| `granite_reasoning_parser.py` | IBM Granite |
| `ernie45_reasoning_parser.py` | 百度文心 |
| `hunyuan_a13b_reasoning_parser.py` | 腾讯混元 |
| `identity_reasoning_parser.py` | "什么都不解析"的占位实现 |

### 解析器的接口

所有解析器继承 `ReasoningParser` 基类，要实现几个关键方法（参考 `deepseek_v3_reasoning_parser.py`）：

```python
class XxxReasoningParser(ReasoningParser):
    # 一次性解析完整输出
    def extract_reasoning(self, model_output, request):
        # 返回 (思考内容, 最终答案)
        ...

    # 流式解析（逐 token 到达时增量解析）
    def extract_reasoning_streaming(self, previous_text, current_text, delta_text, ...):
        ...

    # 判断思考部分是否已结束
    def is_reasoning_end(self, input_ids):
        ...
```

注意有"一次性"和"流式"两套方法——因为 API 既支持一次返回完整结果，也支持流式逐字返回（SSE）。

### 一个有趣的设计：委托模式

看 `DeepSeekV3ReasoningParser`：它自己不实现解析逻辑，而是根据请求是否开启"思考模式"，委托给 `DeepSeekR1ReasoningParser`（解析 `<think>`）或 `IdentityReasoningParser`（不解析）。这是典型的策略委托。

## 二、工具调用解析 (Tool Parser)

### 模型输出长什么样

当模型决定调用工具时，输出里会包含结构化的调用信息，格式因模型而异，比如：

```
<tool_call>
{"name": "get_weather", "arguments": {"city": "北京"}}
</tool_call>
```

### 解析器要做什么

把这段拆出来，转成标准的工具调用对象，让上层应用知道：要调 `get_weather`，参数是 `{"city": "北京"}`。

代码在 `vllm/tool_parsers/`，每个模型同样有自己的解析器（不同模型用不同的标记格式）。

## 为什么这是新手友好的贡献点

每当出一个新模型，往往就需要：

1. 看这个模型的输出格式（用什么标记包裹思考/工具调用）
2. 仿照已有的解析器写一个新的
3. 注册进去 + 写测试

逻辑相对独立、不碰核心引擎、有大量现成例子可参考。这正是你打开的那些文件（`ernie45`、`granite`、`hunyuan` 等）——它们都是同一个模板的不同实现。

## 在主流程里的位置

回顾请求生命周期：解析发生在**输出处理阶段**（`07-请求生命周期.md` 的最后一步之后）。模型生成完文本，detokenize 成字符串，然后解析器把字符串拆成结构化字段，再包装进 API 响应。

## 小结

- 推理解析：把模型输出拆成"思考过程"和"最终答案"
- 工具解析：把模型输出里的函数调用拆成结构化对象
- 每个模型一个解析器，都继承统一基类，支持一次性 + 流式两种模式
- 这是新手友好的贡献方向：逻辑独立、模板清晰、需求持续
