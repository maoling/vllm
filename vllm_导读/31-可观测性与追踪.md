# 31 · 可观测性与追踪 (Observability & Tracing)

> 对应目录：`vllm/tracing/`、`vllm/logging_utils/`、`vllm/v1/metrics/`

## 这个模块负责什么

让你能"看见"vLLM 内部发生了什么，便于排查问题和优化性能。可观测性通常分三块：

| 支柱 | 回答的问题 | vLLM 对应 |
|------|-----------|-----------|
| Metrics（指标） | 系统整体状态如何？ | `v1/metrics/`（见 `22`） |
| Logging（日志） | 发生了什么事件？ | `logger.py`、`logging_utils/` |
| Tracing（追踪） | 单个请求的耗时花在哪？ | `tracing/` |

类比 Web 后端：Prometheus（指标）+ 日志框架（日志）+ Jaeger/Zipkin（链路追踪）这套组合，vLLM 都有对应。

## 1. 日志 (Logging)

`vllm/logger.py` 提供统一的日志器。代码里随处可见：

```python
logger.info("Initializing a V1 LLM engine ...")
logger.warning("Disabling chunked prefill ...")
```

可以通过环境变量调日志级别（`VLLM_LOGGING_LEVEL`）。`logging_utils/` 还提供一些格式化、节流（避免刷屏）的工具，比如 `logger.warning_once`（同样的警告只打一次）。

## 2. 指标 (Metrics)

详见 `22-性能指标与基准测试.md`。要点回顾：引擎每步更新统计（running/waiting 数、KV 使用率、TTFT、吞吐等），通过 `/metrics` 端点暴露给 Prometheus。这是生产监控的核心。

## 3. 分布式追踪 (Tracing)

`vllm/tracing/` 基于 **OpenTelemetry**（业界标准的可观测性框架）。它能记录单个请求在系统里的"时间线"：

```
请求 X 的 trace：
├─ 排队等待        12ms
├─ prefill 计算    45ms
├─ decode（80步）  800ms
└─ 总耗时          857ms
```

把这些 span（时间段）发送到 Jaeger 等后端，就能可视化"时间到底花在哪"，定位瓶颈。

### 怎么开启

```bash
vllm serve <model> --otlp-traces-endpoint http://localhost:4317
```

指定 OpenTelemetry 收集器地址后，vLLM 就会上报追踪数据。

## 这些信息从哪来

回顾 `02-引擎.md` 的 `LLMEngine.step()`，里面那些 `record_function_or_nullcontext("...")` 包裹的代码块，以及第 4 步的 `record stats`——就是在打点采集这些可观测性数据。代码里还有 `iteration_stats`、`scheduler_stats` 等结构在传递统计信息。

## 为什么对生产很重要

部署 LLM 服务，最常见的问题是：

- 为什么这个请求特别慢？→ 看 trace
- 显存够不够、并发到瓶颈了吗？→ 看 metrics
- 服务报错了，发生了什么？→ 看 log

没有可观测性，线上问题基本无法定位。这是从"能跑"到"能稳定运营"的必备能力。

## 对新手的意义

- 本地学习时，看 log 就够了
- 真要部署上线，metrics + tracing 是必修课
- 排查"慢"或"崩"的问题时，先看这三样，别瞎猜

## 小结

- 可观测性三支柱：指标（整体状态）、日志（事件）、追踪（单请求耗时）
- 日志：`logger.py`，可调级别、可节流
- 指标：`/metrics` 给 Prometheus（详见 `22`）
- 追踪：基于 OpenTelemetry，定位单请求瓶颈，上报到 Jaeger 等
- 生产部署的必备能力，本地学习了解即可
