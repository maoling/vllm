# 07 · 请求生命周期（完整串讲）

> 把前面所有模块串成一条完整的流程。建议读完 01~06 后再看这篇。

## 场景

```python
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3-8B")
outputs = llm.generate(["你好"], SamplingParams(max_tokens=100))
print(outputs[0].outputs[0].text)
```

我们跟踪 "你好" 这个 prompt 从进入到输出 "你好！有什么可以帮你的吗？" 的全过程。

## 完整流程图

```
用户: llm.generate("你好")
  │
  ▼
【入口层】 LLM.generate()  →  _run_completion()
  │  ├─ _add_request() ──→ LLMEngine.add_request()
  │  │                        ├─ tokenize("你好") → [108386]
  │  │                        └─ engine_core.add_request(请求对象)
  │  │
  │  └─ _run_engine()：while 还有未完成请求:
  │                        └─ LLMEngine.step()
  ▼
┌────────────────────────────────────────────────────────┐
│  【引擎】 EngineCore.step()  —— 四步循环，反复执行         │
│                                                        │
│  ① 【调度器】 scheduler.schedule()                       │
│     · 把 "你好" 请求从 waiting 移入 running              │
│     · 【KV Cache】 allocate_slots() 分配显存块            │
│     · 输出：本轮处理哪些请求、各多少 token                │
│                                                        │
│  ② 【Worker】 model_executor.execute_model()             │
│     · 准备输入：拼 token、构建 block table                │
│     · GPU 跑模型 forward（调 CUDA kernel）               │
│     · 算出 logits（每个候选词的分数）                     │
│                                                        │
│  ③ 【采样】 sample_tokens()                              │
│     · 应用 temperature / top_p 等                        │
│     · 选出下一个 token，比如 "！"                         │
│                                                        │
│  ④ 【更新】 scheduler.update_from_output()               │
│     · num_computed_tokens += 1                          │
│     · 检查是否到 max_tokens 或遇到结束符 EOS              │
└────────────────────────────────────────────────────────┘
  │
  ▼
【输出处理】 OutputProcessor.process_outputs()
  │  · detokenize：token id → 文字
  │  · 增量拼接到结果里
  ▼
返回用户: outputs[0].outputs[0].text = "你好！有什么可以帮你的吗？"
```

## 分阶段详解

### 阶段 1：请求进入（只发生一次）

1. 用户调 `generate(["你好"])`
2. 入口层为请求分配唯一 ID
3. `LLMEngine.add_request()` 把 "你好" tokenize 成 token id（比如 `[108386]`）
4. 构造内部请求对象，提交给 `EngineCore`
5. 请求进入调度器的 `waiting` 队列

此时：`num_computed_tokens=0`，`num_tokens=1`（prompt 1 个 token）

### 阶段 2：Prefill（第一次 step）

1. 调度器从 `waiting` 取出请求，分配 KV Cache 块，移入 `running`
2. Worker 处理这 1 个 prompt token，跑一次 forward
3. 算出 logits，采样得到第一个输出 token，比如 "！"
4. 更新：`num_computed_tokens=1`，输出 token 数 = 1

> prompt 长就一次处理多个 token；这里 prompt 只有 1 个 token，所以 prefill 很快。

### 阶段 3：Decode（后续每次 step）

每一步 step 生成一个新 token：

1. 调度器给运行中的请求分配 1 个 token 的预算（可能还要新分配 KV 块）
2. Worker 基于已缓存的 KV 跑 forward，算出下一个词的 logits
3. 采样选出下一个 token，比如 "有" → "什" → "么" ...
4. 更新计数，检查是否该停止

如此循环，每步吐一个字。

### 阶段 4：结束

满足任一条件就停止：

- 生成了结束符（EOS token）
- 达到 `max_tokens`（这里是 100）
- 命中停止词（`stop` 参数）

请求标记为 `finished`，调度器调 `free()` 回收它的 KV Cache 块给其他请求用。

### 阶段 5：返回

输出处理器把所有生成的 token detokenize 成完整文字，包装成 `RequestOutput` 返回给用户。

## 关键理解点（最重要）

### 1. step() 是心跳

整个系统就是不停地 `step()`。每一步：所有运行中的请求各自前进一个 token。100 个并发请求，一步就同时推进 100 个请求。

### 2. 一次 generate ≠ 一次计算

用户视角是"调用一次拿到完整回答"，引擎视角是"循环几十上百次 step，每次吐一个字"。

### 3. 显存是核心约束

能并发多少请求，取决于 KV Cache 能切多少块。块用完了就抢占（踢请求）。这是调度器存在的根本原因。

### 4. 共享 GPU 是与 Web 容器最大的不同

Tomcat：一个请求一个线程，独立。
vLLM：所有请求共享一块 GPU，每步打包成一个 batch 一起算。所以需要复杂的调度器来决定 batch 怎么组。
