# 45 · 异步调度与连续批处理优化

> 对应文件：`vllm/v1/core/sched/async_scheduler.py`、`vllm/v1/engine/core.py`（`step_with_batch_queue`）

## 背景：CPU 和 GPU 不该互相等

回顾 `02-引擎.md` 的 `EngineCore.step()` 四步：调度（CPU）→ 执行（GPU）→ 采样（GPU）→ 更新（CPU）。

朴素实现里，这是串行的：

```
[CPU 调度] → [GPU 计算] → [CPU 更新] → [CPU 调度] → [GPU 计算] → ...
              ↑ CPU 闲着        ↑ GPU 闲着
```

GPU 计算时 CPU 闲着，CPU 处理时 GPU 闲着。在 decode 阶段（GPU 单步很快），这种"互相等待"的浪费很明显。

## 优化思想：让 CPU 和 GPU 重叠工作

让 CPU 在 GPU 还在算第 N 步时，就提前准备第 N+1 步的调度。两者像流水线一样重叠：

```
GPU:  [算第1步][算第2步][算第3步]...
CPU:     [调度第2步][调度第3步][调度第4步]...
         ↑ 与 GPU 计算重叠，不再空等
```

这就是 vLLM v1 引擎的重要优化方向，对应几个机制。

## 1. 异步调度 (Async Scheduling)

`async_scheduler.py`。核心思路：**不等上一步的结果出来，就先调度下一步**。

难点：下一步的调度需要知道上一步生成了什么 token（才知道每个请求进展到哪）。异步调度用"占位"的方式先安排，等结果回来再校正。回顾 `03-调度器.md` 里的 `num_output_placeholders`、`next_decode_eligible_step`——就是异步调度留的"占位符"和时序控制。

## 2. 批次队列 (Batch Queue)

`core.py` 的 `step_with_batch_queue()`。维护一个"已提交但还没取结果"的批次队列：

```
提交第1批给 GPU → 不阻塞等结果，立刻提交第2批 → ...
GPU 在排队执行，CPU 持续喂新批次
等队列里第1批结果好了再取
```

这样 GPU 始终有活干，不会因为等 CPU 而空转。

## 3. 和流水线并行的配合

回顾 `08-分布式与并行.md` 的流水线并行（PP）：模型按层切到多卡，本身就需要多个 batch 在流水线里同时流动才能填满。异步调度 + 批次队列正好提供了"同时有多个批次在飞"的能力，和 PP 天然契合。代码里 `next_decode_eligible_step` 那段注释就提到 PP + async 的时序要求。

## 连续批处理（回顾 + 深化）

`03-调度器.md` 讲过连续批处理（continuous batching）：请求能动态进出 batch。异步调度是它的"加速版"——不仅动态组 batch，还让组 batch 这件事和 GPU 计算重叠，进一步压榨吞吐。

```
传统静态批处理：等一批全做完才开下一批（GPU 有空窗）
连续批处理：     请求随时进出（减少空窗）
异步连续批处理： 上面基础上，调度与计算重叠（几乎无空窗）
```

## 代价与权衡

异步调度提升吞吐，但带来复杂度：

- 调度基于"还没确定的结果"做决策，要处理校正逻辑（占位符、回滚边界情况）
- 代码里很多 `deferred_state_corrections_fn`、`num_output_placeholders` 都是为正确性兜底
- 对延迟极敏感的场景，异步带来的"提前调度"偶尔需要微调

这也是为什么这部分代码（调度器、`execute_model`）看起来复杂——它在用复杂度换吞吐。

## 对新手的意义

- 理解"让 CPU 调度和 GPU 计算重叠"这个核心动机最重要
- 这解释了 `03` 和 `05` 代码里那些"占位符""延迟校正"的存在
- 属于性能优化的深水区，先懂动机，细节可后续深入

## 小结

- 问题：串行的"调度→计算→更新"让 CPU 和 GPU 互相空等
- 优化：异步调度 + 批次队列，让 CPU 提前调度，与 GPU 计算重叠（流水线化）
- 代价：基于未定结果做决策，需要占位符和校正逻辑兜底
- 和流水线并行天然契合，是 v1 引擎高吞吐的关键优化
- 解释了调度器/执行代码里"占位符""延迟校正"的由来
